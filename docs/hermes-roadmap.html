The two cracks that block "daily driver"

Before any feature list, two structural problems. If the bet is follow-through, these are the bet. Everything in Phase 0 exists to close them.

Crack 1 — recurring commitments die on completion

A commitment is an ongoing goal ("build the company, monthly"): one row with a cadence. Tapping ✓ flips status to done forever. So the half of the product built for ongoing goals either vanishes when you honor it or nags forever when you don't. Today the only way to keep a commitment alive is to never complete it.

Crack 2 — the escalation has no memory and no consequence

The "Tell your wife" button is a one-tap draft you choose to send. Good for consent. But the referee never enters the loop, nothing records that you told them, and lastNudgedAt is overwritten each cron, so there's no count of how often you ignored an item. Escalation fires on deadline math, not on "you've dodged this four times." That's a louder reminder, not teeth.

The PRDs

Click any card. Each states the problem, the goal, the requirements, and what you'll learn (this is also a build-skills exercise). Full detail lives in docs/hermes-prd.md.

Phase 0 — fix the cracks
P0

PRD-1 · Recurring commitments that survive completion

M · ~6–8h

Problem. Completing a commitment kills it. There's no "did it this cycle, reset the clock, resurface next cycle."

Goal. A commitment is satisfied per cycle, not closed forever. Honoring it resets pressure and schedules the next surfacing.

Requirements

  • Add lastDoneAt; commitment overdue math keys off it, not lastNudgedAt. Nudging and doing become separate signals.
  • ✓ on a commitment sets lastDoneAt = now and keeps status = open.
  • Explicit "retire" path (Telegram retire <id> + board control) to end one for good.
  • Optional cycleStreak for the scoreboard.

Done when

  • A monthly commitment marked done drops in rank, climbs back to burning one cadence later. Retired ones never return. Tasks unchanged.
You'll learn: modeling recurring/stateful entities in a flat schema, and why "done" is ambiguous for anything that repeats.
P0

PRD-2 · Accountability memory

M · ~6–8h

Problem. The system can't tell a new item from one you've dodged five times. No history means no fair escalation and no scoreboard.

Goal. Every nudge, snooze, promise, and completion is recorded. Per item, the system knows how often it pushed and how often you bounced it.

Requirements

  • Add nudgeCount and ignoreCount to Item.
  • Add an append-only Event table (itemId, kind, slot, createdAt) — the audit trail teeth and scoreboard both read.
  • Replace the bare lastNudgedAt write in runSweep with an event + counter bump. Keep buildDailyNudge pure.

Done when

  • Three ignored nudges leave ignoreCount >= 2 and an Event per nudge; the pure builder can change tier from the count with no DB call.
You'll learn: event sourcing basics, append-only audit design, and separating pure decision logic from side effects so it stays testable.
P1

PRD-13a · Test the engine (start early)

S · ~3–4h

Problem. rank.ts and nudge.ts hold the core IP and have zero tests. You're about to change both.

Goal. Lock current behavior before refactoring; start the testing habit on the easiest, highest-value surface.

Requirements

  • Add Vitest; unit-test the pure functions across task/commitment/parking and each tier, with fixed-clock now so HKT logic is verifiable. Wire npm test.
You'll learn: unit testing pure functions, fixed-clock testing for time logic, regression safety nets.
Phase 1 — trust and control
P1

PRD-3 · Freeform edits in natural language

M · ~6–8h

Problem. Capture is freeform, but edits need exact syntax (due 4 2026-06-20). You can't fix a wrong category, type, or referee at all.

Goal. "Push the dentist to Friday", "the gym thing is weekly", "that's a work item, referee my colleague" all just work.

Requirements

  • Extend the classifier into an intent router: create | update | complete | snooze | retire | query, plus which item and fields.
  • Resolve the target by fuzzy title + recent context; if ambiguous, ask one clarifying question rather than guess.
  • Keep exact commands as fast paths; echo the change back.
You'll learn: LLM intent routing, tool-use discriminated unions, disambiguation UX, guarding against confident wrong edits.
P1

PRD-4 · Editable board (full item control)

M · ~8–10h

Problem. The board is done + delete-parking only. You can't fix a misclassification, change a deadline, or reassign a referee from the web.

Goal. The board is a real control surface. Every field Claude guesses, you can correct in two clicks.

Requirements

  • An edit view for every field (deadline stored at 09:00 HKT), server actions for update + retire, inline row quick-actions (snooze, done, edit).
  • Make item type legible at a glance: a cadence marker (e.g. 🔁 weekly) on commitment rows so recurring items read differently from one-off tasks without tapping. Today the only tell is the extra retire control. (Parked 2026-06-18 during the board redesign.)
You'll learn: Next.js server actions for mutation, form state, controlled inputs, date handling across timezones in the UI.
P2

PRD-5 · Smarter snooze and parking promotion

S · ~3–4h

Problem. The only snooze is "1 day". Parking items can't graduate to real tasks.

Goal. Defer with intent (tonight, this weekend, next week, custom) and promote a parked idea into an actionable task.

Requirements

  • Snooze presets computed in HKT; a "promote" action that converts parking → task and asks for a deadline/referee. Surfaced in Telegram buttons and the board.
You'll learn: calendar math in a fixed-offset timezone, progressive disclosure in a constrained UI.
Phase 2 — teeth
P1

PRD-6 · Graduated escalation with real auto-send

L · ~10–14h

Problem. Escalation never reaches the referee unless you tap, and you can ignore the tap. No real consequence. Now fixable because PRD-2 gives ignore-counts.

Goal. A fair, escalating ladder where social cost becomes real only when you've repeatedly, demonstrably dodged something that matters.

Recommended ladder (my call, per your delegation)

  1. Touches 1–2 ignored — normal push: Done / I'll-do-it-today / optional one-tap Tell.
  2. Touch 3+, or 3+ days overdue, or commitment 2 cycles late — escalate: referee button first, blunt copy, plus a warning: "Tap it, or tomorrow I send it for you."
  3. Touch 5+ (or day after the warning) on a critical item with a referee — auto-send through a server-controlled channel, then tell you: "I told your wife. Here's what I sent." One armed item at a time, never silent.

The honest infrastructure note

wa.me links can't be sent server-side; they need a human tap. Real auto-send needs a channel you control: Twilio SMS (simplest, recommended start), WhatsApp Cloud API (on-brand but needs template approval), or Telegram-to-referee (free if they install the bot). Recommendation: ship the ladder with Twilio SMS, keep wa.me one-tap for early touches, gate auto-send behind a per-referee opt-in.

Done when

  • An important task ignored five times with an opted-in referee triggers exactly one auto-send and one owner notification.
  • Without opt-in, copy escalates but never auto-sends. Every step has an Event row.
You'll learn: third-party messaging APIs, idempotency and "fire at most once" guards, consent gating, and designing a system that acts on your behalf without misfiring.
P3

PRD-7 · Referee loop (optional, higher-touch)

L · ~10–12h

Problem. Even with auto-send, the referee is passive. Real accountability lets the other person poke back.

Goal. The referee can confirm they're holding you to it, fire a "did you do it?" back, and get an optional weekly digest.

Requirements

  • A tokenized link (no full account) showing items they referee, a "nudge Jules" button, opt-in weekly digest. All actions logged.
You'll learn: tokenized capability links (access without accounts), designing for a second human in the loop.
Phase 3 — scoreboard
P2

PRD-8 · Follow-through analytics

M · ~6–8h

Problem. The product claims it improves follow-through and nothing measures it.

Goal. A scoreboard from the Event log: completion rate, average days-to-done, ignore rate, streaks.

Requirements

  • Metrics from Events + timestamps; a board section and Telegram stats command showing this week vs last, per category. Computation in a pure, testable module.
You'll learn: turning an event stream into aggregates, choosing metrics that reflect the goal rather than vanity counts.
P2

PRD-9 · Weekly review ritual

S · ~4–5h

Problem. No reflection moment. Things rot silently in the "show all" drawer.

Goal. A Sunday digest: what you finished, what you dropped, what's rotting and needs a decision.

Requirements

  • Fold a weekly branch into the Sunday evening cron (Vercel Hobby caps at two crons/day). Surface stale items with do / schedule / drop buttons. Pull headline numbers from PRD-8.
You'll learn: working within platform limits, designing a forcing function rather than a passive report.
Phase 4 — open the doors (multi-user)

The migration phase. The current code assumes one user everywhere: ownerChatId is the whole auth model, no row is scoped to a person, referees are env vars. Treat this as a deliberate migration, not a sprinkle of userId columns.

P1

PRD-10 · Multi-user data model

L · ~12–16h

Goal. A User entity that owns items, referees, and settings, with strict per-user isolation.

Requirements

  • User (telegramChatId, email?, timezone); Item.userId FK; a Referee table replacing the env-var trio; settings scoped per user.
  • Every query filters by userId; the cron sweeps all users. Migration backfills Jules as user 1. Move to versioned migrations (PRD-17) first.
You'll learn: multi-tenancy, row-level isolation, foreign keys and backfill migrations, the cost of retrofitting tenancy vs designing for it.
P1

PRD-11 · Real authentication

L · ~10–14h

Problem. Board auth is one shared cookie with no expiry, no identity.

Goal. Per-user accounts linked to a Telegram identity, with real sessions.

Requirements

  • Telegram login and/or email magic link (evaluate Auth.js vs a thin custom session); account linking via a code from the bot; session checks replace the global-secret middleware. Webhook keeps its secret guard.
You'll learn: auth flows (sessions, magic links, account linking), authentication vs authorization, why a shared secret isn't auth.
P2

PRD-12 · Onboarding

M · ~6–8h

Problem. Hermes hardcodes Jules's referees, categories, and rules in the system prompt. A new user has none of that.

Goal. A short onboarding capturing identity, referees + channels, quiet hours, timezone, then personalizing the classifier.

Requirements

  • Bot- or web-driven setup; inject per-user context into the classifier prompt instead of the hardcoded Jules block; sensible defaults so a user starts in under two minutes.
You'll learn: parameterizing a hardcoded prompt into per-user config, onboarding as activation.
P2

PRD-18 · Per-user scheduling, timezones, quiet hours

M · ~6–8h

Problem. Nudge times are fixed at 09:00/21:00 HKT for everyone. A user in London gets nagged at 02:00.

Goal. Each user is nudged on their own clock, with quiet hours and weekend rules.

Requirements

  • Generalize startOfDayHKT to startOfDay(date, tz) with stored IANA timezones; the cron fans out to users whose local time matches their slot; per-user quiet hours and no-weekend flag. Re-checks the Vercel cron quota.
You'll learn: correct timezone handling beyond a fixed offset (DST, IANA), fan-out scheduling under platform constraints.
Phase 5 — build it properly (threads throughout)
P1

PRD-13 · Test strategy

M · ongoing

Beyond Phase 0 units: integration tests for the Telegram webhook (mock Telegram, real test DB) and the cron sweep; contract tests on the classifier tool schema. Target the risky paths: callback parsing, escalation gating, multi-user isolation.

You'll learn: the test pyramid, mocking external services, testing time- and side-effect-heavy code.
P2

PRD-14 · CI/CD

S

GitHub Actions runs prisma generate, tsc, vitest, and prisma migrate deploy against a preview DB before Vercel deploys. Block merge on red.

You'll learn: CI pipelines, deploy gates, migration-on-deploy discipline.
P1

PRD-15 · Observability and error handling

M

Problem. The webhook swallows every error and always returns 200; a failed cron send is invisible. Goal. Know when something fails. Structured logging, error tracking (Sentry), and a cron health alert when a sweep finds an owner but fails to send. Keep always-200 for Telegram, but log the underlying error first.

You'll learn: observability, error tracking, the difference between absorbing an error and hiding it.
P1

PRD-16 · Security hardening

M

Close the gaps that are fine for one trusted user and unacceptable for many: rate-limit the webhook and login; validate and bound all inputs; rotate and scope secrets; enable Supabase row-level security as defense in depth; review the auto-send path for abuse; a security pass before opening to others.

You'll learn: rate limiting, input validation, secrets management, defense in depth, threat-modeling a feature that messages people on a user's behalf.
P1

PRD-17 · Migration discipline

S

Problem. The project uses prisma db push with no migration files and has flipped between SQLite and Postgres. Fine solo, dangerous with real user data. Goal. Versioned, reviewable migrations as the only way the prod schema changes. Adopt prisma migrate, commit files, run migrate deploy in CI; settle the dev/prod provider story.

You'll learn: schema migration as a versioned artifact, why db push doesn't scale past one developer.
